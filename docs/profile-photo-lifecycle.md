# Private profile photos

One authenticated human account owns one canonical profile photo, regardless of whether the active persona is patient, healthcare professional, or both. The API accepts only a multipart `file`; ownership comes from the verified session and current account/persona rows. A professional onboarding row is not required.

`POST /api/auth/me/profile-photo` creates or replaces the photo. `GET` on the same path returns a fresh signed GET for the exact active object version with a 300-second lifetime and `Cache-Control: no-store`. A missing photo returns 404. `DELETE` clears the active reference transactionally and returns 202 with `cleanup_status` (`completed` or `pending`). While cleanup is pending, the API cannot mint another URL for the removed photo. A previously issued URL remains valid until its short expiry.

The `profile_photos` row stores the user ID, configured private bucket, opaque key, exact provider version, server-controlled content type, normalized byte size, dimensions, SHA-256, and update time. No provider URL or signed URL is stored. The legacy `users.image` value is neither read nor changed by this lifecycle; it may contain an arbitrary URL and remains a separate compatibility field until #139. Existing clients must call the new endpoint to use the canonical photo. The dashboard, patient web, and mobile are affected consumers of the additive OpenAPI and generated client contract; their adoption is separate from this backend issue.

Each upload gets a fresh random UUID key under `profile-photos/`. Before contacting storage, a delayed `private_object_delete` outbox reservation durably records that key. The storage service uploads normalized bytes and returns a concrete version ID. Activation locks the user and reservation, rechecks account, session and persona, swaps the active row, and queues old-object cleanup in one transaction. An ambiguous upload failure leaves the reservation delayed so a late provider write is still found. A failed activation leaves the reservation for retry cleanup. A successful activation closes and scrubs the reservation. Concurrent activations serialize on the user row. Replacement never deletes the active old object before committing the new reference. Cleanup removes every exact-key version and delete marker and verifies absence. A provider failure leaves a pending event with bounded retry backoff. The existing cleanup maintenance worker must be scheduled during #163's B2 rollout; until then the request tries immediate cleanup and retains failed events for manual retry.

The transport holds at most one file in memory and caps input at 5 MiB. The domain checks the same cap, accepts only declared JPEG, PNG, or WebP matching complete container structure, rejects animation, and decodes with a 16-million-pixel limit. Both image edges must be at most 4096 pixels. It then auto-orients and re-encodes to metadata-free sRGB JPEG at quality 85; output is capped at 5 MiB. An extension, when supplied, must agree with the declared MIME; filenames and supplied metadata are never stored or reflected. The private media bucket uses the #179 provider-neutral storage configuration. Live B2 provisioning and verification remain the #163 activation gate.

Profile-photo objects and metadata are personal data. Removal revokes the active reference immediately, then deletes all object versions; the row is removed rather than retained as history. Outbox cleanup references remain only until successful cleanup and operational outbox retention. Account deletion must remove the photo reference and enqueue cleanup before deleting the user; cross-domain deletion orchestration is outside this issue and must be completed before that account-deletion flow is activated.
